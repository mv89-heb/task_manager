## בדיקות אוטומטיות (CI)
כל `push`/`pull request` ל-`main` מריץ אוטומטית את כל סוויטת ה-pytest דרך GitHub Actions (`.github/workflows/tests.yml`).
אם בדיקה נכשלת, ה-PR/commit יסומן ב-❌ ישירות ב-GitHub - לפני שהקוד בכלל מגיע ל-Render.

## מודל ההרשאות (עודכן)

שלוש רמות תפקיד:
- **admin (מנהל מערכת)** - רואה ומנהל את כל המשתמשים, המשימות והמחלקות במערכת.
- **manager (מנהל תחום)** - רואה ומנהל רק את המשתמשים והמשימות של המחלקה שאליה הוא משויך.
- **employee (עובד)** - רואה ומעדכן רק את המשימות שהוקצו לו אישית.

כל משתמש יכול להיות משויך ל-**מחלקה** (Department) ולבעל **מנהל ישיר** (manager_id, לצורך קו דיווח / עץ ארגוני).
ההרשאה לצפייה נקבעת לפי `role` + `department_id` (ראו `User.visible_users_query()` ב-`app/models/user.py`).

## הרצה מקומית
```
pip install -r requirements.txt
python run.py
```

## פריסה ל-Render
1. Push ל-GitHub (ודאו ש-`.env` לא נכלל - הוא ב-.gitignore).
2. חברו את הריפו ל-Render כ-Web Service.
3. הגדירו משתני סביבה ב-Render: `DATABASE_URL` (מ-Neon), `SECRET_KEY`, `MIGRATION_SECRET`.
4. ה-Start Command הוא `gunicorn run:app` (מוגדר כבר ב-Procfile).

## הרצת בדיקות אוטומטיות
```
pip install -r requirements-dev.txt
pytest -v
```
הבדיקות רצות על מסד SQLite זמני בלבד - לא נוגעות בנתונים אמיתיים. מכסות: הרשאות היררכיות, CSRF, הגנת מנהל אחרון, שדרוג סכימה אוטומטי, ופיצ'רים (משימות חוזרות, תגובות, תמונות).

## סביבת Staging (מומלץ להקמה)
כרגע כל שינוי נבדק ישירות מול נתוני הפרודקשן. מומלץ:
1. ליצור Web Service נוסף ב-Render בשם `task-manager-staging`, מחובר לאותו ריפו אבל ל-branch נפרד (למשל `staging`)
2. ליצור פרויקט Neon נפרד (או branch בתוך אותו פרויקט Neon - יש להם פיצ'ר branching) עם `DATABASE_URL` נפרד
3. לבדוק כל שינוי שם קודם, ולמזג ל-`main` (שמחובר לפרודקשן) רק אחרי שהוא עבד

## משתני סביבה נדרשים ב-Render
| משתנה | חובה | תיאור |
|---|---|---|
| `DATABASE_URL` | כן | חיבור ל-Neon Postgres |
| `SECRET_KEY` | כן | מחרוזת אקראית ייחודית לפרודקשן |
| `ADMIN_USERNAME` / `ADMIN_EMAIL` / `ADMIN_PASSWORD` | לא | פרטי האדמין שנוצר אוטומטית אם אין אחד קיים |
| `MAIL_SERVER` / `MAIL_PORT` / `MAIL_USERNAME` / `MAIL_PASSWORD` | לא | לשליחת מיילים (איפוס סיסמה + תזכורות). בלעדיהם שליחת מייל תיכשל בשקט |
| `REMINDER_SECRET` | לא | מפתח להפעלת `/api/send_due_reminders` דרך cron חיצוני |

## תזכורות יומיות אוטומטיות (מייל + מערכת)
כדי שהתזכורות באמת יישלחו כל בוקר, יש להגדיר קריאה יומית (למשל דרך cron-job.org החינמי) לכתובת:
```
https://<your-app>.onrender.com/api/send_due_reminders?key=<REMINDER_SECRET>&when=today
```
אפשר להוסיף גם קריאה נפרדת ביום שלפני עם `&when=tomorrow` לתזכורת מוקדמת. כל קריאה יוצרת גם התראה פנימית וגם מייל (אם למשתמש יש כתובת מייל מוגדרת).

⚠️ **וואטסאפ/SMS אוטומטיים** (בלי לחיצת אדם) **לא נתמכים** ללא שירות חיצוני בתשלום כמו Twilio - זה דורש אינטגרציה נפרדת. מה שכן קיים: כפתורי "שלח בוואטסאפ" בכל מקום רלוונטי (SOS, הודעות קבוצתיות, תזכורות בדשבורד) שפותחים קישור מוכן ללחיצה אחת.

## מגמות לאורך זמן (גרף בדשבורד)
כדי שגרף "מגמת השלמת משימות" בדשבורד יתמלא בהיסטוריה, יש להוסיף קריאה יומית נוספת (באותו שירות cron):
```
https://<your-app>.onrender.com/api/snapshot_daily_stats?key=<REMINDER_SECRET>
```
מומלץ להריץ בסוף היום (למשל 23:00). הקריאה שומרת תמונת מצב יומית (סה"כ/הושלמו) לכל מחלקה ולכלל הארגון - אידמפוטנטי, אפשר להריץ כמה פעמים באותו יום בלי כפילויות. בלי זה, הגרף יציג הודעת "אין מספיק היסטוריה" עד שיצטברו לפחות 2 ימים של נתונים.

## שליחת מייל תמיד אסינכרונית (ברקע)
כל שליחת מייל במערכת (הקצאת משימה, SOS, הודעות קבוצתיות, תזכורות, איפוס סיסמה) רצה ב-thread נפרד ברקע ולעולם לא חוסמת את התגובה למשתמש. זה קריטי כי SMTP לא מוגדר/לא נגיש עלול לגרום ל-`smtplib` לתקוע חיבור לעשרות שניות (אין timeout קצר כברירת מחדל) - בלי התיקון הזה, כל פעולה שמנסה לשלוח מייל הייתה "נתקעת" עד שהחיבור נכשל. המשתמש תמיד מקבל תשובה מיידית; הצלחת/כישלון המייל בפועל נגלים רק דרך "בדוק הגדרות מייל"/"סטטוס SMTP" בפאנל הניהול או בלוגים.

## אבטחת סיסמאות וסשן
- סיסמה חדשה (הרשמה/איפוס/יצירת משתמש) חייבת לפחות 8 תווים, כולל אות וספרה
- "זכור אותי" בהתחברות: 14 יום; בלי זה, הסשן פג אחרי 12 שעות של חוסר פעילות
- **סיסמאות קיימות לא מושפעות** מהדרישה החדשה - הבדיקה חלה רק כשקובעים סיסמה מחדש, לא בכניסה למערכת
- `/rescue` מסמן אוטומטית את המשתמש לחובת החלפת סיסמה בכניסה הבאה (כי הוא מאפס לסיסמה ידועה `123456`). ניתן לסמן כל משתמש אחר לאותה חובה דרך `/admin/user/<id>/edit` → "חייב את המשתמש להחליף סיסמה בכניסה הבאה"

## יומן ביקורת (Audit Log)
`/admin/audit_log` (admin בלבד) מתעד פעולות רגישות: מחיקת משתמש/מחלקה/תבנית/משימה, שינוי תפקיד, איפוס סיסמה ע"י מנהל, הקצאה קבוצתית, ושימוש בכלי הניהול המסוכנים (`/rescue`, `/fix-db`, `/upgrade-permissions`). לא מתעד כל פעולה במערכת - רק את מה שחשוב לדעת "מי עשה מה" אם משהו משתבש.

## דיווח תקלה ציבורי (בלי התחברות)
`/report` - טופס פתוח לכולם (דיירים/עובדים שאינם משתמשי מערכת), נגיש גם מקישור בדף ההתחברות. מוגן ב-honeypot (שדה מוסתר אנטי-בוט) והגבלת קצב (8 לשעה לכל IP). כשמדווחים תקלה:
- אם נבחרה מחלקה עם מנהל תחום - המשימה מוקצית אליו ישירות, והוא מקבל התראה + מייל
- אם אין מנהל למחלקה (או שלא נבחרה מחלקה) - המשימה עוברת לכל מנהלי המערכת
- פרטי המדווח (שם/טלפון, אופציונליים) מוצגים בברור במסך עריכת המשימה, עם קישור `tel:` ללחיצה ישירה
- משימות שמקורן ציבורי מסומנות בתגית "דיווח ציבורי" בכל הרשימות

טיפ שימושי: אפשר להדביק מדבקת QR עם קישור ישיר ל-`https://<your-app>.onrender.com/report` ליד ציוד/מקומות פיזיים, כדי שדיווח יהיה מיידי בלי להקליד כתובת.

**לשונית עצמאית (`/reported_issues`, admin/manager בלבד):** כל הדיווחים הציבוריים מרוכזים שם, **בנפרד לגמרי** מרשימת המשימות הרגילה (`/`) - אין ערבוב. הלשונית כוללת: קישור מוכן להעתקה לטופס הציבורי, סינון לפי סטטוס, ועדכון סטטוס ישיר. תג אדום בסרגל הצד ("תקלות מדווחות") מציג כל הזמן כמה דיווחים עדיין ממתינים לטיפול.
| `ENABLE_ADMIN_TOOLS` + `MIGRATION_SECRET` | לא | מפעילים יחד את `/fix-db`, `/rescue`, `/upgrade-permissions` - השאירו כבויים בפרודקשן רגילה |
